Feasibility study, 4 October 2026. zui at 667d0aa, Bend 2.0.35 at 565d7fd

Can zui be written in Bend?

Viable, but not fully in Bend

Not fully, and not as a fork in the sense zui is one. A GPUI-style framework whose logic is Bend is viable. That logic covers the element tree, layout, text wrapping, hit testing, input dispatch, entity state and the scene. Bend source cannot call native APIs, so the window, input, IME, clipboard and CoreText calls must be an Objective-C layer of several thousand lines that Bend imports as effects. The pixels should be shaded by a Metal pipeline that draws the Bend-built scene. That design is path P3. In a real Retina window it held 120 Hz on 98.6% of frames. When Bend code shaded the same frame itself, it ran at about 56 Hz.

What "fully written in Bend" can honestly mean

zui is called a Rust framework, and by line count it nearly is. Its macOS build is about 98% Rust and 2% Metal shaders. Its Cocoa, Metal and CoreText calls are Rust because Rust can call Objective-C directly.

Bend cannot do that. Native code enters a Bend program only through .c or .js files that a foreign effect imports, and only the event loop runs them. So every place where zui's Rust calls AppKit, Metal or CoreText becomes Objective-C in a Bend version. That is about 14,000 zui-equivalent lines. Shaders are not the gap, since zui ships them too.

The bars attribute zui's macOS framework (82,541 lines without tests, examples and tooling) to the language each part would be written in. The Bend share lands between 70% and 85% depending on where the boundary goes. It falls to about 69% if platform trait files, the executor and half the text system count as native. It rises to about 85% if taffy, the 22,150-line layout crate a Bend version must also write, counts as Bend. It is a share of responsibilities, not a count of lines anyone has written.

One frame, from keypress to pixels

AppKit owns GPUI's loop and calls stored closures the moment an event arrives. A Bend program owns its own loop and pulls events once per frame. Every step below follows from that inversion.

1ObjC

AppKit delivers key, mouse, scroll and IME events, and the native layer queues them. Typed text goes through interpretKeyEvents into an NSTextInputClient view. That view answers AppKit's synchronous questions from a snapshot Bend pushed last frame.

2ObjC

A drain effect hands the queued events to Bend as one list.

3Bend

Dispatch. Mouse events hit-test against last frame's hitbox list. Keys walk the focus path and keymap, with multi-stroke state held in Bend. Each match yields a Msg value, not a closure call.

4Bend

update(msg, store) rewrites state. Entities are U32 ids into an Array slot table, threaded linearly through the frame.

5Bend

view(state) builds the element tree as a closed sum type, such as Div | Text | Img | List | UniformList.

6ObjC

Text runs missing from the shape cache go to CoreText in one effect call. That costs 0.36 ms for 2,000 characters, or about 10 µs per changed line (measured).

7Bend

Layout. A bottom-up measure pass, greedy word wrap over cached advances, then a top-down place pass for a flexbox subset.

8Bend

Paint emits a flat scene (a quad list and a glyph list), the hitbox list, and the IME snapshot for step 1.

9Metal

The present effect walks the scene lists, encodes instanced draws, and the shaders compute rounded-rect SDFs and borders with hardware blending. The prototype read every field in place from Bend's heap and blocked until the GPU finished. A production version should copy the scene into a packed buffer instead.

10Bend

If nothing changed, block in a wait bounded by Bend's next timer instead of redrawing. That cut idle cost from 13% of a core and 57% GPU use to 1% and 3% (measured). End each frame with IO.sleep(0) so timers and channels run.

Five paths compared

P1 uses only what Bend ships. P2 and P3 are rewrites that differ in who shades the pixels. P4 and P5 are bindings in the style of gpuix, which wraps native GPUI.

Why P3

  • It is the only path that held 120 Hz at Retina with full redraws, so it needs no damage tracking, which is the hardest part of P2.
  • Hardware blending gives alpha and antialiased edges. Blur, shadow and path pipelines can be ported from zui's metal_renderer.rs and shaders.metal.
  • It needs no ! anywhere, which avoids every GPU-lane trap this study hit.
  • Build it with a packed-copy scene buffer, the way GPUI does. That frees the shaders from Bend's internal heap layout and lets CPU and GPU work overlap.
  • Keep a Bend rasterizer (P2-CPU) as the fallback where Metal is absent, such as Linux on X11.

Why not Bend on the GPU

Bend can rasterize on the GPU. Its Slash Boss demo reproduced its documented 8 ms frame here, at 7.2–8.3 ms over 3 × 1,192 frames. UI frames are the wrong shape for it. They are mostly flat, so the parallel work tree is sparse and GPU lanes sit idle. GPU render took 23.9 ms at 4 cards and 5.3 ms at 4,096 cards. Retina multiplies that cost. The framework core cannot run on ! at all. Layout took 14.4 ms at 501 elements and then hit a stack overflow at 2,001.

Is this "a gpuix for Bend"?

Only in purpose. gpuix gives JavaScript a GPUI front end, but it is a binding. It is a 26,125-line Rust napi crate over a GPUI fork (remorses/zed, branch gpuix), driven by a JS reconciler. Every non-Rust GPUI front end found works the same way, including gpui-moonbit and gpui-react. None of them reimplements GPUI.

zui has a different shape. It is one squashed commit that copies GPUI's source with Zed's crate paths kept, so upstream patches still apply with git format-patch | git apply. A Bend version cannot copy that, because no Rust patch applies to Bend source. It would be a GPUI-inspired reimplementation that follows upstream design changes by hand.

If you want apps written in Bend with GPUI's exact pixels, the binding paths (P4, P5) get there faster, and none of the framework is Bend. If you want the framework itself in Bend, take P3.

Risks

What could kill it

  • Upstream churn with no ABI promise. This is the most likely failure. Bend's effect C API is internal by design, and open PR #1281 changes io_eff's signature. Base constructor names are global, and Base's new Scroll broke backplane-bend within a week. Pin a Bend commit and keep the native layer behind a packed-copy boundary.
  • Text-heavy frames. The core timed here uses a fixed advance table and one counter of state. Real shape-cache lookups over String keys, larger glyphs and a real atlas are unmeasured, and they eat the 1.9 ms left in the frame estimate.
  • Allocator slowdown (#1007). It reproduces at HEAD, 2.7× slower on 1 thread and 18× on 12, and it grows with per-frame String churn. The core rebuilding 80,000 characters per frame settled after 200 frames with flat memory over 2,000 frames. Runs longer than 17 seconds were not tested.
  • Text editing depth. IME compositions open across frames, CJK input, candidate-window placement and reconversion are untested.
  • Build loop. No incremental builds, and the JS lane cannot open a window. A 47k-line Bend program took 107 s and 8.6 GB to build natively.
  • Reach. P3 is macOS only. Bend has no Vulkan lane (#811) and does not run on Windows (#788).

Upstream changes that would help

  • PR #1108 adds resizable windows, a Resize event and backing scale. It is open, labeled later, and no longer applies cleanly.
  • #813, a native library target, would make C-to-Bend calls supported. That would fix live resize and synchronous IME queries.
  • U64 (#1027) and F64 (#1120) would map GPUI's ids and hashes directly. Both are listed as planned in WONTFIX.txt.
  • #825, user handle types, would give unforgeable window and renderer handles.
  • #1019 and #1022, typed text and IME in Base, would shrink the native layer.

Effort is a guess. No framework-scale Bend project exists to calibrate against. The nearest is backplane-bend, a 17.7k-line Bend desktop UI written in 8 days by two people, with Claude co-authoring 132 of 229 commits. It is an app, not a framework, and it no longer type-checks under Bend 2.0.35.

Not built yet, even as prototypes: the core and renderer running together, a glyph atlas texture, clipping and content masks, images, shadows, paths, scrolling with clip, async tasks and subscriptions, drag and drop, menus and accessibility.

What the adversarial review changed

Three reviewers on Claude Opus, Fable and Sonnet got the same prompt and tried to break the verdict. Then one agent reproduced the headline numbers alone on the machine. The P3 ranking survived. These corrections are already applied above.

"No missed frames" was false

All three reviewers, plus the reproduction

The first run had 1 of 345 frames over 12.5 ms, and the reproduction had 5 of 345, worst 17.7 ms. The page now says 98.6%.

Safety came from a blocking wait, not the type system

All three reviewers, confirmed by the reproduction

The prototype waits for the GPU before returning the scene to Bend. Without that wait, Bend would reuse the memory while the GPU reads it. The recommendation now says to copy the scene into a packed buffer.

The core and renderer never ran together

All three reviewers

They use different scene layouts, and the core emits 40 times more glyphs than the renderer was timed with. The old "about 3 ms" total became a labeled estimate of 6.4 ms on the critical path.

Core cost climbed within every run

Fable and Sonnet as critical, Opus as a warning

The reproduction ran 2,000 frames. Cost settles 12–26% above the first figures, then stays flat with flat memory. The page uses the settled numbers.

"82% Bend" was presented as a fact

All three reviewers

It depends on boundary choices and swings between 69% and 85%. The page now gives the range, the method, and zui's own 98% for comparison. The lead now answers "not fully".

The 2.55 ms in-window GPU time was called unexplained

Opus diagnosed it, the reproduction confirmed it

The GPU clocks down between vsync-paced frames and overlaps with the compositor. The fastest in-window frame matched headless. Because the prototype blocks, the p90 of 3.5 ms now counts in the frame estimate.

Effort numbers had no derivation

All three reviewers

Month ranges were removed from P3. The page now lists what is unbuilt instead.

Live resize, idle cost and open IME compositions

Opus on resize and IME, the critic on idle

Live resize and the open-composition case are now listed as untested risks. Idle cost was measured. Redrawing every vsync cost 13% of a core, and a timer-bounded wait cut that to 1%.
